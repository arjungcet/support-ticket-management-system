## 1. How the suite runs

- `e2e/` holds Playwright (Chromium) tests. Global setup starts the real processes: the backend jar and `next start`
  on the production build. Tests create data only through the public API or the UI, and scope their assertions with
  a random token.
- The suite runs against two backends:
  - **Real** (`npm run e2e`): the Spring Boot jar. This is the actual verdict on the system.
  - **Contract stub** (`npm run e2e:stub`): `e2e/stub/contract-stub.mjs`, an in-memory, file-backed implementation
    of `spec/api-contract.md`. It is a test tool, not production code. Its purpose is to prove that the tests and
    the frontend are correct while the backend is missing. Otherwise every failure would look the same.

## 3. Failure classification

### Implementation defects

| ID | Defect | Evidence | Affects |
|----|--------|----------|---------|
| **I-1** | **The backend implements none of the API contract.** Every `/api/v1/tickets…` route returns Spring's default `404 {"timestamp","status":404,"error":"Not Found"}` instead of the contract's responses and error format | 19/21 E2E failures (real), 240/241 backend spec-acceptance failures. Every failure message shows the `404` body | Journeys 1–13. Implementation plan STEP-12…39 are not done |
| **I-2** | **Frontend: a stale "changed by someone else — Reload" message stays on screen after the ticket has been reloaded.** `StatusActions` (and likewise `EditTicketForm` and `AssigneeControl`) keep their last error until the next action | Stub run, `J10 after reloading a conflicted ticket, the stale conflict message is cleared`: the alert is still present after reload | UX only. The backend behaviour is correct |
| **I-3** | **Frontend: the backend address is fixed at build time.** `next.config.ts` reads `BACKEND_URL` inside `rewrites()`, which Next.js evaluates during `next build` and stores in `.next/routes-manifest.json` (`destination: http://localhost:8080/...`). Setting `BACKEND_URL` for `next start` is ignored, contrary to `architecture.md` §17 and `frontend/.env.example` | The first E2E run sent every proxied call to `:8080` while the backend was on `:18080`. Confirmed in `routes-manifest.json` | Deployment: one build can't be promoted between environments. The harness works around it by using port 8080 |

### Test defects (found and fixed while building the suite; none open)

| ID | Defect | Fix |
|----|--------|-----|
| T-1 | A bare `getByRole("alert")` also matched Next.js's hidden route announcer (`role="alert"`), causing a strict-mode violation | `appAlert(page)` targets the app's `.alert[role=alert]` |
| T-2 | `check()` on the status checkboxes failed. They are controlled by the URL, so their state changes after the navigation, not synchronously | Click, then `expect(...).toBeChecked()` |
| T-3 | The status-button count included the alert's "Reload ticket" button, which sits in the same region | Count only transition buttons by name. The remaining symptom became I-2 |

### Specification defects

| ID | Defect | Impact |
|----|--------|--------|
| S-1 | **The UI can't produce `TICKET_INVALID_TRANSITION`.** The UI only offers `allowedTransitions`, every status change bumps `version`, and the contract checks version first (`api-contract.md` §1.3). A stale UI therefore always gets `TICKET_CONCURRENT_MODIFICATION`. The "409 invalid transition → show detail, refetch" row in `architecture.md` §6.2 / TS-FE-08 is unreachable from our own UI and only applies to other API clients | Journey 10 is verified through the stale-tab flow (conflict) and a direct API call. Worth noting in the spec so nobody looks for a UI path that can't exist |
| S-2 | The spec doesn't say when a shown error should clear (after reload, next action, navigation) | I-2 is a defect by common UX sense, not against an explicit requirement |
| S-3 | `architecture.md` §17 treats `BACKEND_URL` as runtime configuration without noting that Next.js rewrites are build-time | Led to I-3. The spec should require a runtime proxy (e.g. a route handler) or declare build-per-environment |

### Environment / configuration issues

| ID | Issue | Impact |
|----|-------|--------|
| E-1 | **Docker isn't running** (`/Users/…/.docker/run/docker.sock` missing). There is no PostgreSQL, no Testcontainers and no `docker compose` | Even once I-1 is fixed, journey 13 (persistence) and all DB-backed tests need Docker. Against the stub, J13 only proves the restart mechanics |
| E-2 | The backend has no datasource yet (STEP-08/09 pending), so a restart can't retain data even in principle | Part of I-1 / plan sequencing |
| E-3 | The harness hard-codes `JAVA21_HOME` detection via `/usr/libexec/java_home` (macOS) | CI on Linux must set `JAVA21_HOME` |
